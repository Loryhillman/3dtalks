# 3DTalks — обязательные правила для Codex

> Если в репозитории уже есть корневой `AGENTS.md`, **НЕ заменяйте его этим файлом целиком**. Сначала прочитайте текущий файл, затем аккуратно объедините требования, сохранив существующие инструкции проекта. Проверить вложенные AGENTS.md в изменяемых каталогах.

## Область
Это требования к обычному веб-интерфейсу 3DTalks. 3D-сцена Three.js, модели, анимации внутри мира, управление персонажами, backend, API-контракты и бизнес-логика не меняются в задачах дизайн-системы без отдельного прямого разрешения.

## Перед каждой UI-задачей
1. Прочитать `docs/design-system/README.md` и релевантные документы: `tokens.md`, `layout.md`, `components.md`, `patterns.md`, `responsive.md`, `motion.md`, `accessibility.md`, `page-templates.md`, `governance.md`, `qa.md`.
2. Изучить фактический текущий код и `component-registry.md`; не делать предположений о React, Tailwind, shadcn, расположении файлов и наличии компонентов.
3. Выбрать один из 4 шаблонов Grid/Data/Form/Workspace, если создаётся новая страница; использовать единый App Shell.
4. Переиспользовать существующие компоненты и семантические токены; не создавать собственные новые визуальные стили для конкретной страницы.
5. Поддерживать RU/EN, мобильную адаптацию, клавиатуру и WCAG 2.2 AA.
6. Для форм применять явное сохранение и защиту dirty state; применять общий UX для ошибок/подтверждений/toast.

## Автономность и согласования
- Работа в рамках существующих правил — самостоятельно, без согласования каждой детали.
- **Остановиться и согласовать**, если нужен принципиально новый компонент, дизайн-стиль, motion pattern, layout type, новый UI framework/dependency, несовместимое изменение токенов или архитектуры.
- Не менять business/API/Three.js даже если кажется проще; попросить отдельное разрешение.
- Не подменять реальные серверные операции имитацией UI.

## После каждой UI-задачи
- Провести все применимые проверки из `docs/design-system/qa.md` (визуальная, функциональная, responsive, WCAG 2.2 AA, RU/EN, состояния/регрессии).
- Приложить отчёт `PASS/FAIL/NOT RUN` с основаниями; не заявлять успех непроведённых проверок.
- После утверждённого изменения дизайн-системы обновить соответствующие документы, version, `CHANGELOG.md` и component registry.
- Не выполнять массовый рефакторинг; изменения только в пределах порученной задачи.

## Первое применение (важно)
Прежде чем менять проект, выполнить **аудит без изменений** по `docs/design-system/integration.md`. Предъявить карту файлов, конфликтов и поэтапный план. Дождаться подтверждения пользователем начала первого этапа интеграции.
