# Integration Strategy — постепенное внедрение

## Цель
Сделать документацию нормативной для новых задач, не проводить массовый рефакторинг и не нарушать уже работающий 3DTalks.

## Этап 0 — аудит без редактирования кода
- Определить расположение frontend, стек, маршрутизатор, слой стилей, layout, state-management и i18n.
- Выявить CSS переменные, компоненты, их consumers, существующие тесты и npm/другие команды.
- Проверить реальные API и права для `/rooms`: создание, вход, приглашение, переименование, блокировка, завершение, удаление.
- Проверить поддержку выбора шаблона и источник превью; недоступные функции не имитировать.
- Подготовить карту расхождений (spec vs code), риск и предложение следующей минимальной задачи.
- **Ничего не переписывать на этапе аудита.**

## Этап 1 — документация
- Разместить утверждённые файлы под `docs/design-system/`.
- Если `AGENTS.md` уже существует: дополнить его разделом дизайн-системы, сохранить имеющиеся рабочие/безопасностные инструкции.
- Старый `DESIGN_SPEC.md` остаётся отдельным описанием исходного редизайна; новая система описывает долговременные правила.

## Этап 2 — Design Tokens
- Сопоставить текущие CSS-переменные с Primitive/Semantic без параллельной палитры.
- Измерить контрастность action/color pairs и заполнить доступные semantic токены; скорректировать только соответствующие значения.
- Минимизировать diff; проверить критичные текущие страницы.

## Этап 3 — Component Registry
- Заполнить [component-registry.md](component-registry.md) реальными путями, вариантами, consumers и состояниями; не объявлять Stable без проверки.

## Этап 4 — поэтапная унификация
- Вносить изменения при разработке нового UI или явном утверждённом исправлении несоответствия.
- Принципиальные новые компоненты — proposal/approval, не создавать заранее «на всякий случай».
- Изменения общих компонентов тестировать на всех потребителях.

## Этап 5 — Design QA
- Использовать существующие средства тестирования в первую очередь.
- Playwright/axe-core/Stylelint и т. п. предлагать только после проверки стека; установка новых зависимостей — по согласованию.

## Этап 6 — поддержка
- После каждой UI-задачи соответствующий [qa.md](qa.md) отчёт.
- После изменения правил: обновить документацию, версию и CHANGELOG.
- Следить за Deprecated потребителями и не проводить автоматическое удаление.

## Защитные границы
Не менять протоколы/API, backend, авторизацию и маршруты бизнес-процессов, 3D рендеринг, модели, сцену или перемещение персонажей в рамках этой инициативы. Отдельные конкретно порученные задачи могут изменить границу только при явном разрешении пользователя.
