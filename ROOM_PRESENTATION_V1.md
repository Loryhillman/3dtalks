# Общий экран: PDF и изображения

Дата: 16 октября 2026. Этап 1 — аудит и контракт. Это спецификация, не
реализованная функция. Ветка `codex/room-presentations` от `25dba3a0`.

Пользователь подтвердил первый объём: PDF и изображения, загрузка и управление
у владельца, общий слайд у участников и увеличенный просмотр. Видео, аудио,
делегирование ведущему, PPTX, внешние ссылки и демонстрация рабочего стола
в этот объём не входят. Этот документ уточняет первую версию прежнего
`ROOM_MEDIA_PLAN.md`; предложенные там cookie, лимиты и роль ведущего для неё
не применять автоматически.

## 1. Что подтвердил аудит

- `RoomScene` принимает только геометрию и GLB. Новый экран должен пройти
  серверную валидацию, создание снимка, DTO редактора и обе точки рендера.
- `roomTemplateSession` и `roomEditor` считают все обычные объекты мебелью;
  общий масштаб, копирование, замена модели и выбор родителя места требуют
  явного ограничения для экрана.
- Права HTTP-комнат сейчас допускают чтение открытой комнаты по slug.
  Это недостаточное разрешение на приватные документы.
- Подтверждённый userId соединения есть в `seatIdentities`, само соединение —
  в `activeConnections`, комната — в `playerPositions`. Полномочия нельзя
  брать из имени персонажа, payload.roomId или присланного ownerId.
- Вход и жизненный цикл сериализованы `runRoomOperation`. Завершение сначала
  фиксируется в БД и только потом вызывает `endRoom`. Показ необходимо
  сбрасывать в той же SQL-транзакции, а доступ соединений отзывать сразу.
- `roomEpochs` существует только в памяти. Для нового состояния показа
  требуется собственный сохранённый epoch, переживающий перезапуск.
- Модели стандартного образца находятся в неизменяемом `meeting-six-v1`.
  Его редактирование сломает проверку manifest SHA-256 на установленных базах.
- Проверка границ сейчас проверяет точки предметов, не углы экрана и не
  видимость за мешами. Сервер размещён на VPS примерно с 1 ГБ RAM.

## 2. Экран в шаблоне и созданной комнате

Общий чистый модуль `public/js/roomScreen.js` используется Node и браузером.
Layout содержит не более одного такого объекта; отсутствие экрана допустимо.

```json
{
  "type": "presentation_screen",
  "kind": "screen",
  "name": "Экран",
  "collision": false,
  "position": { "x": 7.5, "y": 2.4, "z": -3.1 },
  "rotation": { "x": 0, "y": -1.5707963267948966, "z": 0 },
  "scale": { "x": 1, "y": 1, "z": 1 },
  "screen": { "version": 1, "width": 3.2, "height": 1.8 }
}
```

- Позиция — центр полотна, метры; фронт — локальная +Z. Поворот только по Y,
  scale всегда 1. Размер задаётся шириной/высотой, не масштабом мебели.
  Ширина 0.5–8 м, высота 0.3–4.5 м; координаты в прежних пределах ±10000 м.
  Пресеты 16:9/4:3 и собственный размер. Числа конечны; лишние поля отклоняются.
- У экрана нет model_id, model_path, geometry components, мест и коллизии.
  Его нельзя копировать, превратить заменой модели в мебель, включить в
  групповой масштаб или назначить родителем места. Удаление в черновике допустимо.
- Runtime: `world_objects.type = presentation_screen`, добавочное nullable
  JSONB `presentation_screen`. Для этого типа model_path — NULL. Проверить
  фактическую nullable-схему и все ограничения type перед миграцией;
  существующие строки не переопределять. SQL CHECK связывает метаданные с типом,
  collision=false и единичным масштабом. Число экранов защищает частичный
  уникальный индекс по room_id. Общий модуль проверяет вложенную форму.
- Публикация и диагностика проверяют центр и четыре угла по общей математике
  RoomEnvironment/RoomEnvelope с прежним допуском 1 см. Для старой непонятной
  оболочки сохраняется предупреждение о визуальной проверке.
- Материал без зависимости от света, содержимое вписывается с полями.
  Обратная сторона непрозрачная; оборот не показывает зеркальный текст.
  В редакторе есть тестовая сетка, знак фронта и собственная панель экрана.
- Увеличенный просмотр — доступный dialog с Escape, удержанием/возвратом фокуса
  и мобильной прокруткой. События его кнопок не вращают камеру; стрелки слайдов
  не перехватывают ввод в чате. Закрытие dialog не меняет общую страницу и место.
- Указанные координаты — кандидат у торца стола встроенного образца.
  Утверждать их можно только после рендера настоящего офиса и проверки с шести
  мест. Проверка углов не доказывает отсутствие стены/колонны перед экраном.
- Редактирование первой версии — в шаблоне. Прямое добавление/перемещение
  экрана в существующей пользовательской комнате не вводится.

## 3. Права, файлы и соединения

| Действие | Кто допускается |
|---|---|
| Размещение экрана и публикация | Администратор шаблонов |
| Список/загрузка/удаление материалов, личный предпросмотр | Владелец этой комнаты с JWT |
| Начать показ, сменить страницу, закончить показ | Владелец с действующим подключением к этой комнате |
| Текущий материал и увеличенный просмотр | Участник с действующим подключением к этой комнате |

Административный токен не становится правом читать чужую библиотеку.
Участнику не выдаётся весь список файлов владельца: только текущий показ.
Закрытый вход не прекращает доступ уже допущенных участников.

После успешного входа сервер отдельно отправляет случайное разрешение
`ROOM_PRESENTATION_SESSION`: 32 случайных байта, связано с connectionId,
проверенным userId, roomId и сохранённым epoch. Оно не попадает в рассылку
участников, URL, localStorage и журналы. Хранится в памяти вкладки и сервера.

Каждый запрос участника к материалу требует обычный JWT и заголовок
`X-Room-Session`. Сервер сверяет активный socket, userId, roomId, epoch,
неистёкшее занятие места и разрешённый текущий assetId. Удержанное место после
disconnect не даёт доступа. Старая вкладка теряет право сразу при замене сессии.
Для предпросмотра владельца используется отдельный owner-only HTTP-маршрут.

Изображение читается fetch → Blob; PDF.js получает httpHeaders. Дополнительные
cookie и bearer-токены в query string для этой версии не нужны. PDF.js
документирует httpHeaders и рендер страницы в canvas:
[API PDF.js](https://mozilla.github.io/pdf.js/api/draft/module-pdfjsLib.html),
[примеры](https://mozilla.github.io/pdf.js/examples/).

Файлы — в `uploads/room-media`, вне public, уже внутри тома /app/uploads.
Только серверные случайные имена. Выдача `private, no-store`, `nosniff`,
фиксированный Content-Type; без express.static и внешних URL.
При выходе, замене сессии, logout и end отменяются чтения и рендер, очищаются
canvas, Blob URL и локальное разрешение. Уже полученные байты отозвать нельзя.

## 4. Стартовые лимиты и подготовка

Это консервативные настройки первого выпуска для небольшого VPS; хранить их
централизованно. Увеличивать после измерений, не произвольно в интерфейсе.

| Ресурс | Предел |
|---|---|
| PDF | 20 МиБ, 100 страниц, без шифрования/пароля |
| PNG/JPEG/WebP | 8 МиБ, 16 млн входных пикселей, один статический кадр |
| Подготовленное изображение | WebP, вписать без обрезки в 2560 px и 4 млн пикселей |
| Библиотека владельца по всем комнатам | 100 МиБ и 20 материалов, включая резервы/удаляемые файлы |
| Все комнатные материалы сервера | 1 ГиБ, включая резервы и ожидающее удаления |
| Одновременные загрузки | 1 на владельца, 2 на процесс |
| Проверка файлов | 1 задача на процесс, очередь максимум 4 |
| Передача загрузки | 30 секунд простоя, 120 секунд всего |
| Проверка одного файла | 10 секунд; превышение завершает задачу ошибкой |
| Canvas текущего слайда | Максимум 4 млн пикселей, сторона не более 4096 |

Один image-файл — один материал с одной страницей. Несколько изображений
можно загрузить отдельно и выбирать для показа; сборка альбома и сортировка
его слайдов в первый выпуск не входят.

Проверка идёт по содержимому, не по расширению/MIME. Изображения декодировать
с лимитом пикселей, применить EXIF, удалить метаданные, отклонить анимацию.
PDF разбирать отдельным ограниченным дочерним процессом; не в Express event
loop и не только регулярным поиском /Page. Число страниц определяет сервер.
Проверить размеры страниц и обычные/повёрнутые/нестандартные документы.

До добавления зависимости — испытать и закрепить одну версию PDF.js и worker
на Node 20 и настоящем клиенте. Проверить комплект шрифтов/CMap/WASM и размер
образа; не подключать CDN. Отключить eval/XFA и не создавать PDF viewer с
интерактивными действиями, вложениями, формами и ссылками. Сервер не растеризует
все страницы и не декодирует картинки PDF для предпросмотра.

Heap лимит дочернего Node-процесса — 96 МиБ, дополнительно родитель наблюдает
RSS процесса и завершает его при 256 МиБ. Heap-флаг сам по себе не ограничивает
native memory/ArrayBuffer. Проверку порога/тайм-аута и завершение дочернего
процесса испытать на целевой Linux-среде до включения upload PDF.

## 5. Состояния хранения и восстановление

`room_media_assets`: id, room_id, owner_user_id, kind, display_name,
storage_key, state, reserved_bytes, byte_size, page_count, checksum, error_code,
lease_until, timestamps. Состояния:

`reserved → uploading → checking → ready → deleting → удалено`.
Из первых трёх разрешены `failed/cancelled`; повторное удаление безопасно.

Перед записью HTTP-файла резервируются заявленные bytes и слот под блокировкой.
Загрузка обязана соответствовать заявленному размеру; лишние байты, второй файл
или неверный тип отклоняются. HTTP-повтор не запускает вторую обработку.
Новая попытка после ошибки получает новую заявку. Контроль квоты нельзя
обходить параллельными комнатами одного владельца.

После проверки файл переименовывается в окончательный случайный путь, затем
в транзакции становится ready. Если процесс упал между этими операциями,
уборщик удаляет файл просроченной заявки и освобождает резерв. Если файл не
удалился, его байты продолжают занимать квоту. Журнал ошибок и результаты
заявок также ограничиваются числом/сроком; не создавать бесконечную таблицу failed.
Периодическая уборка ограничена по числу файлов и не сканирует/удаляет
пользовательские каталоги моделей и аватаров.

Протокол загрузки: POST reserve с requestId/kind/name/bytes, затем POST upload
одного multipart file по uploadId. Резерв истекает через 2 минуты до начала
передачи, работающий upload продлевает lease в пределах общего deadline.
Идемпотентность reserve хранится 15 минут; то же requestId с другим телом — 409.
Недостаток места/квоты/очереди сообщается до загрузки содержимого.

## 6. Показ, ревизии и гонки

`room_presentation_state`: room_id PK, epoch UUID, revision bigint,
asset_id nullable, page_index (0-based), updated_by, updated_at.
Презентационное состояние не хранится в template/layout или avatar_config.

Команды `show {assetId}`, `page {pageIndex}`, `stop {}` содержат requestId,
expectedEpoch и expectedRevision. Первый show начинает с 0; у image индекс 0.
Источник прав/комнаты — проверенное подключение, не поля payload.

- Новый участник получает полное состояние, а не историю команд.
- Контроллер может получить снимок раньше загрузки RoomScene. Он сохраняет
  только последний снимок и применяет его после появления экрана; отсутствие
  экрана не запускает скачивание файла. Stop/exit инвалидирует и это ожидание.
- При конфликте ревизии сервер возвращает 409 и актуальный снимок. Клиент
  обновляет экран; отклонённую команду автоматически не переотправляет.
- Повтор requestId с тем же телом возвращает прежний результат без повторного
  применения. Ключ результата: room_id + epoch + requestId. Журнал — максимум
  256 записей комнаты, TTL 15 минут. Проверка полномочий предшествует replay.
- Commit предшествует рассылке. Получив событие, клиент сравнивает roomId,
  epoch, revision и поколение socket. Устаревший render/fetch не заменяет новый.
- При reconnect, возвращении вкладки и конфликте — запрос целого снимка.
  При смене epoch принимается только снимок актуальной сессии.
- Один текущий render task и ограниченный кеш. При смене страницы отменить
  старый render перед использованием того же canvas. PDF.js явно предупреждает
  о параллельном рендере разных страниц в один canvas в своих примерах.
- Масштаб увеличенного просмотра локальный; участник не меняет общую страницу.
  CanvasTexture обновлять после завершения рендера, не пересоздавать каждый кадр:
  [Three.js CanvasTexture](https://threejs.org/docs/pages/CanvasTexture.html).
- Ошибка декодирования видна конкретному участнику и не останавливает остальных.
  Потерянный файл не должен превращать всю переговорную в ошибку загрузки сцены.

Показ и end проходят через `runRoomOperation`. Порядок SQL-блокировок:
owner (только для операций владельца/квоты) → advisory 73421 → rooms →
presentation state → общий бюджет → assets. Все пути, включая удаление комнаты,
завершение загрузки и уборку, обязаны соблюдать этот порядок; разбор файлов
и передача по сети идут за пределами транзакции/общей очереди.

Close входа сохраняет слайд и epoch. End в одной транзакции сбрасывает показ,
меняет epoch и очищает права встречи; библиотека остаётся владельцу для
следующего открытия. Delete дополнительно ставит файлы/резервы на удаление.
Удаление активного материала требует явного подтверждения stop+delete;
отключение asset от показа и tombstone атомарны, unlink — после commit.
Если все участники вышли, PDF/image сохраняет текущий слайд. Перезапуск сервера
сохраняет слайд, но требует нового входа и нового разрешения на выдачу.

## 7. HTTP и WebSocket

| Транспорт | Новый контракт |
|---|---|
| HTTP owner JWT | `GET /api/my/rooms/:id/materials` — список |
| HTTP owner JWT | `POST /api/my/rooms/:id/materials/uploads` — reserve |
| HTTP owner JWT | `POST /api/my/rooms/:id/materials/uploads/:uploadId/file` — один multipart file |
| HTTP owner JWT | `GET /api/my/rooms/:id/materials/uploads/:uploadId` — состояние заявки |
| HTTP owner JWT | `DELETE /api/my/rooms/:id/materials/uploads/:uploadId` — отмена |
| HTTP owner JWT | `GET /api/my/rooms/:id/materials/:assetId/content` — личный preview |
| HTTP owner JWT | `DELETE /api/my/rooms/:id/materials/:assetId` — удаление |
| HTTP участника JWT + X-Room-Session | `/api/rooms/:slug/presentation/materials/:assetId/content` |
| WS запрос | `ROOM_PRESENTATION_GET_STATE` |
| WS изменение владельца | `ROOM_PRESENTATION_COMMAND` |
| WS адресные ответы | `ROOM_PRESENTATION_SESSION`, `ROOM_PRESENTATION_RESULT` |
| WS снимок/рассылка комнаты | `ROOM_PRESENTATION_STATE` |

Подмаршруты uploads регистрируются перед параметром :assetId. Delete активного
материала принимает `stopShowing=true`, expectedEpoch/revision и requestId;
без этого возвращает MATERIAL_IN_USE. Не перегружать PATCH комнаты и прежний
публичный /api/media. PDF в пределах
20 МиБ первая версия может получать целиком защищённым GET; HTTP Range и
cookie для будущего video/audio — отдельное расширение.
WS несёт только метаданные: payload до 4 КиБ, 2 команды/с с burst 6,
общие прежние пределы соединений/байтов остаются. Для новой команды обязателен
whitelist `roomSocketPolicy` и обработчик `meetingSocket`, без legacy обхода.

Envelope WS-команды: `{requestId, expectedEpoch, expectedRevision,
command: {type: 'show', assetId}}`, либо `type: 'page', pageIndex`, либо `type: 'stop'`.
Адресный result содержит requestId, success, code и актуальный state при конфликте.
Снимок: `{roomId, epoch, revision, asset: null | {id, name, kind, pageCount},
pageIndex}`. Session-разрешение доставляется отдельным адресным сообщением,
не включается в state. На GET_STATE нужен requestId, комната берётся из socket.

Ошибки: 400 INVALID_SCREEN/INVALID_COMMAND, 401 UNAUTHORIZED,
403 PRESENTATION_FORBIDDEN, 404 ROOM_NOT_FOUND/MATERIAL_NOT_FOUND,
409 PRESENTATION_CHANGED/REQUEST_ID_REUSED/MATERIAL_IN_USE/MEDIA_QUOTA_EXCEEDED,
413 FILE_TOO_LARGE, 422 INVALID_PDF/ENCRYPTED_PDF/TOO_MANY_PAGES/INVALID_IMAGE,
429 UPLOAD_BUSY, 503 MEDIA_STORAGE_FULL/PROCESSOR_BUSY.
Ответы не раскрывают пути диска и параметры чужой комнаты. Все UI-сообщения
имеют согласованные ключи трёх каталогов i18n.

## 8. Новый стандартный образец

Только после работоспособного показа создать комплект `meeting-six-v2` с экраном.
Версия 1 и её контрольные суммы не меняются; GLB берутся из прежнего комплекта
через явные доверенные ссылки на его asset keys, без повторной загрузки моделей.
На чистой установке выбирается актуальный комплект; установленный v1 продолжает
восстанавливать собственные файлы, но не получает автоматическую перепубликацию.
Серверные номера версий 8/9 не становятся номерами встроенного комплекта.

Для существующего сервера Артёма: администратор добавляет экран в черновик,
публикует и создаёт новую комнату. Комната `123` и другие снимки остаются прежними.
Ни миграция, ни startup не вставляют экран в чужую действующую встречу.

## 9. Этапы и приёмка

1. **Аудит/контракт — текущий этап.** Границы подтверждены пользователем;
   решения выше зафиксированы, код продукта не изменён.
2. **Экран:** общий контракт, миграция, редактор, snapshots и runtime,
   тестовая картинка и увеличенный просмотр. Старые комнаты продолжают работать.
3. **Материалы:** испытание закреплённого PDF.js на Node 20, приватные upload/
   preview/content, квоты/lease/очистка, клиентский PDF/image renderer.
4. **Общий показ:** серверная авторизация, ревизии/повторы, адресные разрешения,
   поздний вход/reconnect, end/delete/замена вкладки и очистка клиента.
5. **Образец и приёмка:** v2, положение экрана в настоящем офисе, полный цикл
   чистой установки и повторного запуска, две комнаты/аккаунты, документация.

После каждого законченного этапа — diff, профильные тесты, английский коммит
в прошедшем времени и push этой ветки. Следующий этап согласуется с пользователем.
Развёртывание и изменение работающего шаблона на VPS требуют отдельного поручения.

Обязательные негативные сценарии: второй экран; масштаб/коллизия/seat-parent;
выход угла за границу; чужой asset/roomId; JWT без участия; held/заменённая вкладка;
неактуальный epoch; конкурирующие page/end/delete; повтор requestId с другим телом;
разрыв upload и падение до/после rename; отсутствующий/повреждённый PDF;
пароль/100+ страниц/огромные картинки; занятая очередь/квота/диск; timeout/RSS;
смена слайда до завершения старого render; exit/logout во время загрузки.

Проверки разделять честно: чистые модули; отдельная тестовая PostgreSQL с
повторными миграциями и гонками; реальный Express/JWT/Multer; настоящий Chromium
с тестовыми API; полный HTTP/WS/SQL-сценарий нескольких участников. Финально
проверить PostgreSQL 18 в изолированном Compose и мобильный браузер. Рабочую БД,
пользовательские файлы и серверные комнаты в автотестах не использовать.
