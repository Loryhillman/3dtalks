# Развитие переговорной: участники, звук и управление встречей

Версия спецификации: 1.0, 20 октября 2026.
Первый этап: codex/meeting-room-controls, от 58b6b9e6.
Закреплённый результат: checkpoint/pre-webrtc-2026-10-20 (2c6660aa).
Будущие WebRTC-этапы: отдельная codex/livekit-webrtc от 2c6660aa.
Работающий сайт закреплён отдельно; см. [RELEASES.md](RELEASES.md).
Документ описывает целевое поведение всех шести улучшений и границы первого
реализуемого этапа. Разделы будущих этапов не являются отчётом о готовности.
Дизайн: docs/design-system/README.md; существующие ограничения показа:
ROOM_PRESENTATION_V1.md. Учётные данные и серверные секреты сюда не включаются.

## 1. Задача и последовательность

Пользователь подтвердил работающий голос, PDF и изображения. Следующая цель:
сделать ежедневную встречу понятной и управляемой, сохранив комнаты, места,
аватары, личную библиотеку, общий экран и действующие права владельца.

Целевые возможности:
1. Список участников, собственное состояние связи и индикация звука.
2. Проверка/выбор микрофона, а затем нормальный потоковый разговор и mute.
3. Серверная модерация: запрет публикации аудио, удаление и запрет возвращения.
4. Временная передача управления показом.
5. Демонстрация окна/экрана.
6. Поднятая рука и последовательная очередь выступления.

Первый законченный этап: список участников и настройки/локальный тест звука
поверх существующей передачи фрагментов. После него — проверяемый коммит,
отчёт и согласование следующего этапа. Переход на потоковый транспорт —
отдельный этап с инфраструктурной проверкой, а не косметическая замена кнопки.

## 2. Что фактически имеется сейчас

- Node.js/Express/PostgreSQL и один WS-процесс; клиент vanilla JS/Three.js.
  Добавлять React или новый UI-фреймворк для этих панелей не требуется.
- Создание пользовательской комнаты ограничено 1–6 участниками
  (src/services/userRooms.js). Места допускает сервер; список локальных мешей
  не является достоверным каталогом пользователей.
- WORLD_STATE содержит серверный снимок участников, включая себя;
  PLAYER_JOINED/PLAYER_LEFT — изменения присутствия.
  WSPresenceGuard восстанавливает вход и убирает устаревшие аватары.
- VOICE_START/END/STATE обозначают запись, а VOICE_MESSAGE несёт целый base64
  фрагмент MediaRecorder после остановки. Минимум 1 с, максимум около 60 с.
  VOICE_STATE=true означает «записывает», а не «остальные уже слышат».
- Одновременная запись ограничена настройкой relay. Звук ограничен комнатой
  и расстоянием 30 м; клиент применяет затухание. Это наследие PTT,
  его нельзя незаметно превратить в безусловный аудиопоток.
- toggleMute сейчас управляет входящим воспроизведением, не микрофоном.
- Установленный VPS имеет около 1 ГБ RAM и уже обслуживает приложение,
  PostgreSQL, Nginx и резервное копирование. Это измеренное состояние,
  а не оценка достаточности ресурсов для нового медиасервера.
- Owner/canControl общего показа уже проверяются сервером. Локальная кнопка
  «Ведущий» не даёт права расширить выдачу приватных материалов.

## 3. Выбор технологии для потокового этапа

### Принятое решение

Целевая архитектура: WebRTC через отдельный SFU LiveKit, браузерный JS SDK
и Node server SDK с закреплёнными совместимыми версиями. Точную пару версий
проверить в spike перед добавлением зависимостей; не использовать latest/CDN.
Комнаты и роли остаются продуктом 3DTalks, SFU отвечает только за медиа.

Планируемые пакеты: livekit-client для браузерного адаптера и
livekit-server-sdk для Node. Existing UI остаётся vanilla JS. Клиентский SDK
собирать отдельным локальным vendor bundle через уже имеющийся esbuild,
с закреплённым package-lock/лицензиями, без runtime CDN и переписывания
остального фронтенда на React/Vite. Зафиксировать воспроизводимую команду,
выходной файл и его cache key. Приватный server SDK/секреты в public не попадают.
Будущее добавление runtime-пакетов потребует полноценной сборки Docker-образа;
прежний приём COPY поверх старого runtime для этого не подходит.


Это инженерный выбор с учётом будущей модерации и демонстрации:
одна публикация участника поступает SFU, а не отдельная копия каждому соседу.
Медиасервер способен прекращать публикацию при отзыве разрешения.
LiveKit документирует удаление опубликованных треков при отзыве CanPublish:
[participant management](https://docs.livekit.io/intro/basics/rooms-participants-tracks/participants/).
Включить микрофон пользователя удалённо нельзя: разрешено только предложить
ему включиться самому.

### Рассмотренные альтернативы

| Вариант | Решение и причина |
|---|---|
| Нынешние целые записи по WS | Сохранить до миграции; не выдавать за realtime. Крупные base64 пакеты и отправка после stop не подходят для постоянного микрофона |
| Резать MediaRecorder на короткие chunks | Не выбирать как постоянный транспорт: нужны корректные контейнеры/декодирование, буферизация, потери, порядок и контроль задержки |
| Native WebRTC mesh на 6 человек | Подходит для эксперимента; 15 пар связей и до пяти исходящих копий экрана у ведущего. Без центрального media enforcement усложняет требуемую модерацию и последующий рост |
| WebRTC + SFU | Выбранная цель для совместного аудио, контроля публикаций и единственного демонстратора |
| Самописный SFU или перенос всего приложения | Не требуется для задачи; создаёт лишнюю эксплуатационную/протокольную работу |

Числа mesh — расчёт n(n−1)/2 для n=6, не результат нагрузочного теста.
Нельзя обещать задержку, ёмкость или стоимость до измерений.

### Развёртывание и сеть

SFU размещать отдельно от текущего app/DB: отдельный VM или выбранный
пользователем управляемый сервис. Платный аккаунт/тариф не подключать
автоматически. Не считать RAM текущего VPS подходящей без замеров.
Self-hosted сначала проверить в отдельном тестовом окружении; HTTPS/WSS,
ICE/UDP и TURN/TLS должны быть реально доступны с внешних сетей.

TURN нужен как рабочий relay для сетей, где прямой ICE-путь недоступен;
одного успешного теста в домашнем Wi-Fi недостаточно. Обоснование ICE/TURN:
[WebRTC peer connections](https://webrtc.org/getting-started/peer-connections).
Сетевые диапазоны и firewall брать из выбранной конфигурации SFU,
а не открывать порты «на всякий случай»:
[LiveKit ports](https://docs.livekit.io/transport/self-hosting/ports-firewall/).
Это отдельные media-порты; HTTP reverse proxy приложения их не заменяет.

Redis/кластер/egress/запись встреч в первую конфигурацию не добавлять без
обоснования. Горизонтальное масштабирование app всё ещё требует вынесенного
presence и доставки событий; появление SFU само по себе этого не решает.

## 4. Разделение ответственности

- HTTP/WS: аутентификация, валидация, доставка, ограничение размеров/частот.
- Meeting service: допуск, роль владельца, presenter grant, ban, состояние руки.
- PostgreSQL: долговечные ограничения/роли/запреты, транзакции и журнал команд.
- Presence: активная серверная сессия/место; WS-соединение не равно свободному
  пропуску в SFU.
- Media adapter: выпуск коротких room-scoped grants, управление публикациями,
  обработка событий медиасервера, reconciliation.
- Browser audio session: треки, выбранные устройства, попытки подключения,
  autoplay, pending операции и освобождение ресурсов.
- Roster store: данные/состояния; отдельная HTML-панель отображает их.
  В store не должно быть Three.js или создания аватаров.

Не переносить создание участников сцены в HTML-панель и не читать meshes
для определения присутствия. Не добавлять универсальную event-bus архитектуру
ради двух компонентов: явные методы и подписки достаточны.

## 5. Общая компоновка

Сохранить компактную верхнюю карточку: имя комнаты, места, выход, язык,
управление экраном. Добавить одну строку из двух вторичных кнопок:
«Участники · N» и «Звук». На desktop/телефоне одинаковый порядок действий.

«Участники» открывает native dialog с компактной шапкой, счётчиком,
состоянием собственной связи и прокручиваемым списком.
«Звук» — такой же dialog с устройством и локальной проверкой.
Открывается одно из двух окон; открытие другого закрывает предыдущее.
App Shell на /play не добавляется. Панели не перекрашивают canvas/редактор.

Desktop ширина около 440–520 px; mobile — ширина viewport минус 24 px,
max-height — видимая область минус 24 px. Header фиксирован внутри окна,
контент прокручивается; контролы не уходят за клавиатуру/малый landscape.
Токены/Inter/цвета/контраст — из app-controls/app-tokens.
Кнопки минимум 44×44, поля 16 px. Новая высокая «бровь» не требуется.

## 6. Строка участника

Первая строка — собственный пользователь с меткой «Вы», далее остальные
по отображаемому имени/стабильному id. Не переставлять строки на каждом
начале/конце голоса: чтение и управление должны оставаться предсказуемыми.

Строка содержит:
- имя (без HTML, перенос длинных слов; полное значение доступно);
- собственную метку;
- текстовый audio status; цвет/иконка только дополняют текст;
- после серверного расширения — проверенную роль и доступные действия.

Первая версия не добавляет аватарки из произвольных URL и не запрашивает
GLB для списка. Визуальные персонажи остаются в существующей 3D-сцене.

## 7. Честные состояния присутствия

Список строится из серверных WORLD_STATE и PLAYER_JOINED/LEFT. Snapshot
заменяет прежний набор целиком; недостающие участники не остаются призраками.
Повторные join одного characterId не создают дубликат. Не показывать токены,
connectionId, IP или userId. Пустой/некорректный payload не ломает панель.

До первого snapshot: «Подключаемся…», счётчик неизвестен, не «в комнате 0».
После snapshot: «Соединение установлено». При потере своего WS:
«Восстанавливаем соединение; список может быть неактуален».
Не приписывать каждому удалённому человеку «плохой интернет» — этих данных
пока нет. Held seat — зарезервированное место, не подтверждённый онлайн.

При reconnect очистить активные recording/playback сигналы. После нового
snapshot убрать stale и показать актуальный набор. При выходе/end/смене
аккаунта закрыть панели, очистить store/таймеры и прекратить локальные тесты.

## 8. Индикация голоса до WebRTC

| Источник | Что показывать |
|---|---|
| Принят VOICE_STATE=true | «Записывает сообщение» |
| VOICE_STATE=false или TTL/leave | Снять запись; это не означает начало воспроизведения |
| Успешно запущен AudioBufferSource | «Воспроизводится сообщение» у отправителя |
| Воспроизведение закончилось/остановлено | Снять playback; учитывать перекрывающиеся источники одного человека |
| Только членство, но нет сигналов | «В комнате», без выдуманного статуса микрофона |
| Собственная запись | «Вы записываете»; отказ/остановка немедленно снимают индикацию |

Recording TTL — защитный предел около 70 с, не heartbeat присутствия.
Playback определяется фактическим запуском звука, не моментом получения
VOICE_MESSAGE: декодирование/autoplay может задержаться или завершиться ошибкой.
Не скрывать индикацию в свернутом диалоге на уровне данных; при открытии
показывается актуальный state. Не генерировать aria-live на каждый audio frame.

## 9. Выбор микрофона — первый этап

В «Звук»: пояснение про текущую отправку записи, подписанный select
«Микрофон», «По умолчанию», найденные audioinput и «Проверить микрофон».
При первом открытии enumerateDevices не должно запрашивать разрешение.
До разрешения реальные имена могут быть скрыты: использовать «Микрофон 1»
и т. п., не считать пустые label ошибкой.
Ограничения enumerateDevices/devicechange — в спецификации
[Media Capture and Streams](https://w3c.github.io/mediacapture-main/getusermedia.html).

Выбор хранится только в браузере как deviceId, без имён/отпечатков в логах
и без отправки на сервер. Хранение может быть недоступно; настройки не должны
из-за этого падать. «По умолчанию» удаляет предпочтение.

Для явно выбранного id использовать exact. Если устройство исчезло —
показать понятную ошибку и предложить выбрать другое/«По умолчанию»;
не включать незаметно другой микрофон. Обрабатывать devicechange,
NotAllowedError, NotFoundError, NotReadableError, OverconstrainedError,
отсутствие mediaDevices и незащищённый контекст.

Смену устройства не применять посреди записи: выключить select с объяснением,
дождаться остановки. Перед реальной записью прекращать локальный тест.
При ошибке разрешения доступна новая явная попытка после изменения настроек
браузера; нельзя снимать серверный crowded deny как будто это mic error.

## 10. Локальная проверка микрофона

После явного нажатия запросить только audio, echoCancellation/noiseSuppression;
не запрашивать камеру. Показать «Запрашиваем доступ…», затем индикатор уровня,
«Проверка идёт только на вашем устройстве» и кнопку «Остановить».
Проверка не отправляет VOICE_START/VOICE_MESSAGE и не создаёт blob/файл.

AudioContext + MediaStreamAudioSourceNode + AnalyserNode; source не соединять
с destination, чтобы не было обратной связи. Для уровня достаточно RMS
несколько раз в секунду, без отдельного canvas/Three.js renderer.
Не трактовать нулевой уровень как доказанный отказ устройства.

Не допускать одновременную capture-сессию теста и настоящей записи.
При close/Escape, новом тесте, смене устройства, скрытии вкладки,
disconnect/end/stop остановить tracks, meter timer и AudioContext.
Тест ограничен по времени (30 с); pending запрос разрешения можно инвалидировать,
но нельзя программно закрыть системный prompt. Запоздалый grant немедленно
останавливает все полученные tracks, не возвращает закрытую панель.
Проверять гонку close -> reopen -> новый grant отдельно.

В первом этапе дополнительно доступен выключатель входящего воспроизведения,
с точной подписью «Слышать участников». Это не состояние публикации микрофона.
Отключение сразу останавливает текущие источники, не только будущие сообщения.

## 11. Потоковый микрофон — следующий этап

По умолчанию после входа/переподключения микрофон выключен.
Основная кнопка — toggle «Включить микрофон / Выключить микрофон».
Рядом в настройках режим PTT: удержание мышью/касанием/Space, release/pointercancel/
lostcapture/blur прекращают публикацию. Клавиша M — только вне полей,
диалогов с вводом и IME; для первой версии shortcut можно не добавлять.

Нельзя заменять режим микрофона на отключение динамиков. Оба состояния
видны раздельно. Самопроизвольное включение после reload, devicechange,
ошибки, снятия модераторского запрета или reconnect запрещено.

Состояния audio session: idle/muted, requesting-permission, connecting,
publishing, muted-by-owner, recovering, failed, stopped.
Отдельный userIntent и generation/AbortController для каждой попытки;
stopped терминален. Старый callback не имеет права включить новую сессию.

Mute прекращает передачу, а UI различает это и освобождение устройства.
Для privacy-stop/выхода tracks.stop обязателен. Если SDK временно держит
выключенный track для быстрого unmute, интерфейс не должен обещать, что
аппаратный индикатор микрофона погас. Выбранную политику проверить в браузерах.

## 12. Кто говорит при WebRTC

Сигнал активного говорящего берётся из audio/SFU events с hysteresis:
краткие паузы не должны мигать, фоновый шум не должен переключать список.
Показать обводку/индикатор у имени, текст «Говорит», при возможности — над
аватаром. Первым источником истины для mute/publish являются media-события,
не класс кнопки.

Текст «Микрофон выключен» допустим только при подтверждённом состоянии.
Audio-level — это оценка энергии, не распознавание речи/содержания.
Не хранить сырые уровни в SQL, не отправлять их в основной room WS на каждый кадр.
Пока SFU не внедрён, не использовать этот термин для legacy recording state.

## 13. Вход и выдача медиа-разрешения (проект контракта)

Это будущий контракт, не существующий endpoint:
POST /api/rooms/:slug/media/session, обычный JWT + живой room session claim.
Сервер проверяет пользователя, активное место/допуск, session epoch, ban
и разрешения, затем выдаёт краткоживущий SFU token (целевой TTL порядка 60 с
для начала подключения), endpoint и mediaSessionId.

Identity строит сервер из доверенной учётной записи и конкретного поколения
подключения. Клиент не задаёт чужой identity, media room или canPublish.
Разрешить только join/subscribe и допустимые audio/screen sources.
Запретить административные/room-create права клиентскому токену.
Секрет SFU — только server env, token — в памяти вкладки, не URL/localStorage/лог.

Короткий TTL токена сам по себе не закрывает уже открытое медиа-соединение:
при end/delete/kick/ban/session-replaced обязательно принудительное удаление
из SFU, отзыв публикации и периодическая сверка. Webhook подпись проверяется;
события идемпотентны, устаревшие mediaSessionId игнорируются.

Обычный WS остаётся транспортом чата/мест/ролей. SDPs, ICE и видео не передавать
как base64 через существующий room WS. SFU SDK ведёт свой media signaling.
До успешной admission/grant выдачи ни публикации, ни подписки.

## 14. Надёжность и ошибки медиа

При потере WS медиа закрывать/снимать публикацию: нельзя оставлять звук
между пользователями после утраты продуктового допуска. Повторное соединение
не восстанавливает включённый микрофон без явного решения пользователя.
Не запускать legacy clips и realtime одновременно; режим задаёт сервер
на комнату/сессию, клиент показывает точную причину недоступности.

Autoplay error => видимая кнопка «Включить звук», await play()/resume(),
без вечного тихого успеха. Браузерный permission deny отделяется от сетевого ICE
failure и от запрета владельца. Нет устройства — отдельная диагностика.
Device switch: создать новый допустимый track, заменить через SDK,
после успеха остановить старый; при failed не продолжать захват скрыто.
Запоздалые callbacks нового/старого track/room не должны менять другую сессию.

Retry с backoff и верхним пределом, не бесконечные параллельные подключения.
Сетевые логи — состояние/коды, без SDP, IP candidates, JWT и содержимого аудио.
Нагрузочные метрики: CPU/RSS, RTT/jitter/packet loss, TURN ratio, число rooms/
publishers/subscribers. До замеров — никаких обещаний числа параллельных встреч.

## 15. Модерация

Действия владельца в строке другого участника:
«Запретить микрофон», «Разрешить включить микрофон», «Удалить со встречи»,
«Удалить и запретить возвращение». Владелец не может удалить себя этой кнопкой.
Чистое удаление и ban — разные последствия с отдельным текстом подтверждения.

Сервер проверяет owner по rooms.owner_user_id, живую сессию, целевого участника,
revision/requestId и состояние комнаты. Запретить роль владельца из payload.
После commit доставить событие и выполнить media enforcement через SFU.
При частичном отказе не сообщать «участник отключён», пока медиа не отозвано;
повтор операции идемпотентен, UI показывает pending/ошибку.

Для ban хранить room_id/user_id/reason(optional)/created_by/created_at/revoked_at
с уникальностью активного ban. Проверять при WS admission, HTTP media grant,
восстановлении места и выдаче материалов. Удалить действующие claims и rejoin
grants, отозвать SFU-session. Простого закрытия WS недостаточно.
Для «разрешить» вернуть право, а не включить чужой микрофон.
Не реализовывать скрытое прослушивание/remote capture.

## 16. Передача презентации

Владелец остаётся владельцем библиотеки. Presenter — временная роль конкретного
активного участника, а не новый owner. Единственный presenter grant на комнату,
со своим revision/epoch. Владелец может отозвать его в любой момент.

Безопасная первая версия: presenter управляет текущими разрешёнными материалами
владельца; явный allowlist с точным описанием, что участник сможет увидеть.
Личная библиотека владельца не раскрывается целиком.
Загрузка «своих материалов ведущего» — отдельное расширение с собственной
квотой/владением/cleanup, не неявное чтение чужой библиотеки.

Переиспользовать existing expectedEpoch/expectedRevision/requestId.
canControl вычисляет сервер для владельца и действующего presenter grant;
disconnect/end/kick/revoke обнуляют временное право, pending commands больше
не применяются. Все WS commands и HTTP content checks учитывают новую роль.
Материалы не клонируются и не переводятся в public uploads.

## 17. Демонстрация экрана

Только после потокового транспорта. Одновременно один screen publisher;
владелец или разрешённый presenter. «Поделиться экраном» вызывает
getDisplayMedia из явного жеста. Браузер выбирает экран/окно/вкладку;
приложение не выбирает область за пользователя.

Первая версия: видеотрек экрана без гарантии system/tab audio. Без захвата
камеры. Целевые ограничения 1280×720/15 fps как начальная конфигурация,
проверить читаемость/CPU/bitrate на выбранном SDK; это не SLA качества.

Общий экран имеет взаимоисключающие режимы idle/material/screenShare.
Переключение атомарно по room revision; поздняя демонстрация старого presenter
не замещает новый PDF. Stop через кнопку приложения, браузерный stop или
track.ended одинаково очищает публикацию и video texture.
При восстановлении соединения демонстрация не запускается без нового жеста.
Локальный увеличенный viewer получает изображение того же опубликованного
источника; не добавляет вторую публикацию и не меняет режим комнаты.

VideoTexture принадлежит сцене/экрану, video element/media track — media session:
отдельно освобождать обе стороны. Предыдущие PDF/изображения остаются в личной
библиотеке; нет автоматического экспорта содержимого демонстрации.

## 18. Поднятая рука

Кнопка toggle «Поднять руку / Опустить руку». Сервер назначает монотонную
последовательность/время и возвращает snapshot очереди; клиентское время
не определяет приоритет. Собственная рука отражается без оптимистического
постоянного успеха до подтверждения.

Показать badge и номер в списке; не переставлять основной каталог участников.
Владелец видит очередь и может снять руку конкретного человека.
Кик/end/session-replaced/длительный disconnect удаляют её; при коротком
reconnect политика удержания должна быть явной. Первая версия — снять
при утрате активной room session; новый вход не поднимает руку автоматически.
Лимит один запрос от участника, ограничение частоты, без хранения бесконечного
журнала кликов. Если хранить в процессе — документировать поведение при restart.

## 19. Совместимость и безопасность изменений

Сохранять снимки комнат, мебель/места, существующий presentation_screen,
канонические встроенные GLB и выпущенные комплекты. Не обновлять старые
комнаты/seed на месте. Новые поля — аддитивные миграции с повторным запуском.
Ни модерация, ни медиатокены не должны обходить roomScope и существующую
изоляцию материалов/чата/голоса.

RoomSocketPolicy расширяется точечно: размеры/частоты новых контролов,
без наследования лимита аудиопакетов. SFU grants — rate limit отдельно.
Для потокового режима старый VOICE_MESSAGE должен быть отключён сервером,
а не только скрыт в UI; иначе останется обход модерации.

SQL locks: согласованный owner -> room/seat порядок существующих сервисов;
не делать сетевой SFU RPC внутри долгой SQL-транзакции.
Для критических команд использовать transactional outbox/reconciliation
с явно отражённым pending media enforcement, не ложную атомарность SQL+SFU.
Приватные device labels, аудио и личные материалы не писать в логи.

## 23. Проверка потокового этапа перед выпуском

Обязательны 2 и 6 браузеров, forced TURN relay, запрещённый UDP, потеря WS,
потеря SFU, отказ токена/просрочка/ban, старый tab replacement, owner force mute,
отзыв presenter, экранный track ended, смена устройства во время grant,
снятие mute без автоматического capture, отсутствие двойного legacy/realtime.
Наблюдать память/CPU несколько часов; метрики качества и budget определить
из измерений, не копировать чужой benchmark.

Тесты с моками и локальный SFU не заменяют реальные внешние сети.
Серверный rollout — feature gate, резервная копия, предыдущий образ,
контроль ready + media connectivity и ясный rollback без изменения старых
снимков/материалов. В случае отказа сохранить текст/показ и показать точную
причину недоступности звука, не переключать транспорт незаметно.
