# 3dtalks

Переговорные комнаты в браузере: кабинет пользователя, вход по ссылке,
посадочные места и административный редактор шаблонов помещений.

## Запуск

Нужны Docker Engine и Docker Compose.

Единый файл настроек для локального запуска и сервера — `.env` в корне проекта.
Compose читает его автоматически; `--env-file` в обычных командах не нужен.
После клонирования создайте файл настроек:

```bash
cp .env.example .env
```

Заполните в `.env` четыре обязательных параметра:

| Параметр | Значение |
|---|---|
| `WORLD_URL` | Адрес сайта, например `http://localhost:3002` |
| `DB_PASSWORD` | Пароль PostgreSQL |
| `ADMIN_USERNAME` | Логин первого администратора |
| `ADMIN_PASSWORD` | Пароль первого администратора: от 12 символов, до 72 байт UTF-8 |

```bash
docker compose up -d --build
```

Откройте http://localhost:3002. Админка: http://localhost:3002/admin_login.html.
После входа `/admin.html` открывает управление переговорными: комнаты и
шаблоны, загрузка мебели в библиотеку GLB, список пользователей, профиль
администратора и язык для новых посетителей. Список пользователей доступен
для просмотра; старые действия с RPG-персонажами и удалением аккаунтов отключены.
База, первый администратор, внутренние секреты и шаблон переговорной создаются
автоматически. Дамп и скачивание демонстрационных моделей для новой установки не нужны.
Первый запуск включает сборку образа и может занять несколько минут.

### Стандартная переговорная в новой установке

В проект включён готовый образец: GLB-офис, стол, шесть стульев, настроенные
посадочные места и экран для общего показа PDF/изображений. При первом запуске на чистой базе он становится стандартным
шаблоном для новых комнат. Три файла моделей занимают около 4,5 МБ; скачивание
с сервера автора и импорт чужой базы не нужны.

Актуальное описание хранится в `database/seeds/meeting-six-v2/manifest.json`.
Оно ссылается на три исходных GLB неизменяемого `meeting-six-v1`, не дублируя
файлы. Установка проверяет SHA-256, копирует файлы в записываемый том
моделей и регистрирует их в библиотеке с локальными идентификаторами. Поэтому
комплект работает и с новым, и с уже существующим Docker-томом. Повторный запуск
не создаёт дубликаты; отсутствующий файл установленного комплекта восстанавливается.
Файл с несовпадающей контрольной суммой не перезаписывается: запуск сообщает ошибку.

**Обновление существующей установки сохраняет её оформление.** Если стандартный
шаблон уже редактировали или публиковали, либо по нему создавали комнаты,
стартовый образец поверх него не устанавливается. Установленный образец можно
менять в редакторе и публиковать обычным способом. Существующие комнаты сохраняют
прежние снимки. Сброс базы или томов для применения обновления не требуется.
Уже установленный комплект v1 продолжает восстанавливать собственные файлы;
v2 поверх него автоматически не публикуется. На старой установке администратор
может добавить экран в черновик шаблона, опубликовать его и создать новую комнату.

Проверка полного SQL-пути в **отдельной тестовой PostgreSQL**:

```bash
ROOM_TEST_DATABASE_URL='postgresql://USER:PASSWORD@HOST/TEST_DB' node scripts/check-room-builtin-postgres.js
```

Скрипт использует временные схемы и проверяет повторную миграцию, одновременную
установку, восстановление файлов, откат транзакции, сохранность правок и снимков.
Рабочую базу для него не используйте. Браузерная проверка настоящих моделей:
`node scripts/test-meeting-startup-browser.js --builtin` — Three.js и клиент
настоящие, HTTP/WebSocket-данные тестовые.

Compose запускает приложение в режиме переговорных (`APP_MODE=rooms`).
В этом режиме отключены API большого мира и RPG, федерация серверов,
подключение AI-агентов и архивирование их чата. Старые API генерации сцен,
AI-провайдеров, галерей, медиа и настройки погоды также не подключаются.
Кабинет, комнаты, редактор
шаблонов, загрузка моделей и пользовательские аватары работают независимо
от этих старых подсистем. Существующие модели и записи в базе не удаляются.
Мебель загружается через редактор комнат с авторизацией администратора;
прежний публичный `/api/upload-model` в этом режиме недоступен.

WebSocket в режиме переговорных ограничивает размер и частоту сообщений,
а также очередь отправки медленным клиентам. На один процесс допускаются
до 256 соединений, из них до 32 ожидающих входа в комнату; на вход даётся
30 секунд. Это технические пределы сервера, отдельно от вместимости комнаты.
Превышение лимитов закрывает соединение. Голосовые сообщения до 2 МБ base64
поддерживаются; параметры защиты заданы в `src/websocket/roomSocketPolicy.js`.

Страница переговорной `/play?room=…` использует сокращённый набор скриптов:
модули RPG, федерации, погоды и редактора большого мира не загружаются.
Вход запускается через отдельный `meetingMain.js`, без старого `main.js`.
Мышь и касание экрана управляют обзором; клавиши движения и боя отключены.
Участник использует отдельный контроллер посадки без RPG-состояния. Цикл
переговорной не запускает LOD, погоду, порталы и загрузочные очереди большого мира.
Сообщения комнаты обрабатывает отдельный клиент: посадка, аватары, чат и голос.
Старые события RPG, погоды и смены шаблонных персонажей в комнате игнорируются.
Аватар берётся из аккаунта; старый выбор шаблона персонажа в браузере на него
не влияет. Микрофон работает отдельной кнопкой: удерживайте её и отпускайте
для отправки записи. Можно использовать пробел или Enter, когда кнопка в фокусе.

Помещение загружается целиком: стены, мебель и коллизии не исчезают при
удалении от них. Повторяющиеся GLB в одной комнате скачиваются один раз.
Если модель недоступна, вход показывает ошибку загрузки помещения; частично
загруженные объекты удаляются. Подробности ошибки отмечены `[RoomScene]`
в консоли браузера.

Если запуск не удался, выполните `docker compose logs --tail=100 app`.
Ошибки настроек отмечены `[CONFIG]`: указаны имя параметра и требование к нему,
без вывода паролей. Отсутствующие обязательные значения Compose покажет сразу
в терминале, до создания контейнеров. После исправления `.env` повторите
`docker compose up -d`; простой `restart` не применяет изменения `.env`.

- [Локальная разработка без постоянной пересборки](LOCAL_DEVELOPMENT.md)
- [Запуск на сервере и обновление](SERVER_DEPLOYMENT.md)

Для **существующей установки** сохраните текущий пароль базы и Docker-тома.
Не заменяйте свой `.env` примером. Переход с прежних конфигураций описан в
инструкции локальной разработки.

## Аватар пользователя

В кабинете откройте **«Мой аватар»**. Можно выбрать стандартное тело с головой
в виде картинки, шара, куба или отдельной GLB-модели; также можно загрузить
персонажа целиком. Предпросмотр использует ту же модель тела и посадку, что и
переговорная. После сохранения внешний вид применяется при следующем входе в
комнату и виден остальным участникам. Настройки привязаны к аккаунту, а не браузеру.

- Изображение: PNG/JPEG/WebP до 8 МБ, обрезается до квадрата по центру.
  На шаре и кубе изображение располагается на плоской передней панели.
- Голова: GLB без скелета, до 20 МБ и 30 000 треугольников.
- Персонаж целиком: GLB до 40 МБ и 100 000 треугольников, с одним совместимым
  человекоподобным скелетом. Нужны таз, голова и цепочки бедро–голень–стопа;
  распознаются названия костей Mixamo и варианты `Hips_01`, `Head_06`,
  `Upper_Leg_L_063`, `Lower_Leg_L_064`, `Foot_L_065` (также правая сторона).
  Пространства имён и числовые суффиксы экспортера учитываются автоматически.
  Допускаются несколько `skins` для частей тела и одежды одного скелета;
  неоднозначные кости и отдельные несвязанные скелеты отклоняются.
- GLB должен содержать все ресурсы внутри файла. Текстуры — до 4096×4096,
  не более 32 изображений и 16 млн пикселей суммарно. Draco, Meshopt и KTX2 в редакторе аватаров не поддерживаются.
- Лимит на аккаунт: 12 файлов и 100 МБ. Ненужные файлы можно удалить;
  файлы сохранённого аватара и активного сеанса защищены от удаления.

Модели автоматически приводятся к стандартным размерам. Направление модели,
размер и высоту головы можно поправить в предпросмотре. Проверка скелета не
гарантирует идеальную посадку любой модели: итог зависит от её пропорций и
привязки геометрии к костям. Анимации из загруженного GLB пока не воспроизводятся.

Настройки хранятся в PostgreSQL, файлы — в `/app/public/uploads/user-avatars`
в существующем томе загрузок. При переносе на другой сервер нужны база и этот
том; `git push` файлы аватаров не переносит. Миграция базы применяется при запуске.

## Готовый офис GLB в шаблоне

В административном редакторе **шаблона** откройте «Помещение»:

1. Загрузите офис через «Загрузить офис GLB» либо выберите его в библиотеке
   и нажмите «Подготовить модель». Для этой загрузки геометрия и текстуры не
   упрощаются и не сжимаются автоматически.
2. Оцените предпросмотр. Укажите ширину в метрах — общий масштаб изменится
   пропорционально. Поворот задаётся вокруг Y; X/Z размещают модель в комнате.
3. Укажите уровень поверхности пола внутри модели и внутренние границы.
   Их координаты показаны в метрах **до переноса и поворота**. Указанный уровень
   пола будет совмещён с мировой высотой Y=0. Габариты файла могут включать
   толщину стен и декор, поэтому предложенные границы требуют проверки.
4. Подтвердите границы и нажмите «Применить помещение». Отдельные предметы
   и места сохранят свои мировые координаты; проверьте, что они внутри офиса.
5. Сохраните черновик и опубликуйте шаблон. Новые комнаты получат новую версию;
   существующие комнаты сохранят прежние снимки. В самой созданной комнате
   переключение основного помещения недоступно.

Во вкладке «Посадочные места» выберите место: редактор покажет стандартного
сидящего персонажа в масштабе игры. Его можно скрыть отдельным переключателем.
Проверьте высоту сиденья, направление взгляда и положение ног относительно стула.

Во вкладке «Помещение» при подготовке и настройке GLB также есть отдельный
сидящий персонаж для сравнения размеров. Он сохраняет игровой масштаб при
изменении офиса. X/Z смещают его от центра помещения по мировым осям,
Y задаёт высоту точки посадки над выбранным полом, поворот — направление взгляда.
«Приблизить персонажа» подводит камеру. Ориентир не создаёт место и не сохраняется
в шаблоне; точную посадку проверяйте на выбранном настоящем месте.

Панель «Проверка расположения» отмечает доступные места и точки привязки
предметов за границами, отсутствующие привязки и места ближе 20 см друг к другу.
Ошибочные места выделены красным, соответствующие строки — красной рамкой.
Проверка обновляется при редактировании и подготовке нового помещения;
ошибки блокируют публикацию, но позволяют сохранить незавершённый черновик.
Она не определяет пересечения мешей и не гарантирует, что голова или ноги
каждого пользовательского аватара не пересекутся со стеной: это проверяется визуально.

Нужен статический самодостаточный GLB 2.0 с одной сценой, без скелета,
анимаций, внешних ресурсов и сжатия Draco/Meshopt/KTX2. Лимиты: 100 МБ,
300 000 треугольников с учётом экземпляров, 128 материалов, 64 изображения;
сторона текстуры до 4096 пикселей, суммарно до 32 млн пикселей.
Набор мебели не становится готовой комнатой автоматически: стены и пол
должны присутствовать в выбранном офисе. Встроенные предметы остаются частью GLB.

«Отменить подготовку» возвращает текущую обстановку. Уже загруженный файл
может остаться в общей библиотеке; отмена не удаляет его. Возврат к собранному
помещению в той же вкладке восстанавливает предыдущую распознанную оболочку.
После перезагрузки вкладки создаётся базовая оболочка 12 × 10 × 3.5 м;
старые опубликованные версии и комнаты продолжают хранить свои снимки.

### Масштабирование нескольких предметов

В редакторе **шаблона** выберите предметы Ctrl/⌘-кликом в списке или сцене.
Можно включить «Выбирать несколько предметов» и выбирать обычными кликами;
повторный клик снимает выбор. Esc или «Снять выделение» очищает весь выбор.

В панели «Общий масштаб» задайте коэффициент: `0.5` уменьшает вдвое,
`2` увеличивает вдвое. Размеры и расстояния меняются относительно среднего
положения выбранных предметов; пропорции и повороты сохраняются. Вся операция
проверяется до применения: допустимый масштаб по каждой оси — 0.01–100,
координаты — ±10000 м. Затем сохраните черновик и опубликуйте шаблон.

Это временный выбор отдельных предметов, а не разбор мешей внутри GLB.
Основное помещение меняйте через его собственные настройки. Независимые места
остаются на своих координатах; прикреплённые следуют за переносом предмета,
но их локальное смещение не масштабируется. После изменения проверьте посадку.

### Приёмка готового офиса

Для существующей локальной установки сохраните текущий `.env` и данные.
Обновите приложение в режиме разработки:

```bash
cd /root/projects/3d-virtual-world
docker compose -f compose.yaml -f compose.dev.yaml up -d --build
```

Затем выполните один полный цикл:

1. Откройте существующую комнату и сохраните её ссылку для сравнения.
   Если комнат ещё нет, создайте одну до публикации нового шаблона.
2. Войдите в админку, в разделе шаблонов откройте редактор стандартной
   переговорной. Обновите страницу через Ctrl+Shift+R.
3. Во вкладке «Помещение» загрузите **готовый офис со стенами и полом**.
   Настройте размер, уровень пола и внутренние границы, подтвердите их
   и примените помещение. `low_poly_meeting_room_assets.glb` содержит мебель,
   поэтому для этого шага нужен другой файл с самим помещением.
4. Расставьте минимум шесть доступных мест — это требование стандартного
   шаблона. Выбирайте каждое место и проверьте посадку стандартного аватара,
   направление взгляда и высоту. Отдельная прежняя мебель сохраняется:
   удалите ненужные предметы в редакторе, если они дублируют мебель внутри GLB.
5. Временно переместите одно место за границы: оно должно подсветиться,
   а публикация — блокироваться. Верните его внутрь, устраните остальные
   ошибки расположения, сохраните черновик и опубликуйте шаблон.
6. В кабинете создайте **новую** комнату и войдите в неё. Нужен свободный слот
   из пяти сохранённых комнат. Убедитесь, что загружен офис, прежняя оболочка
   не накладывается на него, места видны и их можно занимать/менять.
7. Откройте прежнюю комнату по сохранённой ссылке: её оформление и места
   должны остаться прежними. Публикация не обновляет уже созданные комнаты.

Автоматические проверки прошли с изолированными API и имитацией БД.
Этот цикл проверяет настоящие файлы и сохранение в вашей PostgreSQL.
Отдельная проверка миграций и конкурентных SQL-операций перед развёртыванием:
задайте `ROOM_TEST_DATABASE_URL` **отдельной тестовой базы** и запустите
`node scripts/check-room-template-editor.js`. Скрипт создаёт временную схему
и удаляет её после проверки; рабочую базу для теста не используйте.

## Проверка после очистки клиентского сценария

В dev обновите вкладки через Ctrl+Shift+R; в обычном режиме обновите образ
по инструкции запуска. Проверяйте двумя разными аккаунтами в разных браузерах:

1. Войдите в кабинет, создайте комнату и скопируйте приглашение.
2. Войдите по приглашению вторым аккаунтом. Проверьте обстановку, оба аватара
   и имена; старые настройки персонажей не должны менять их внешний вид.
3. Поменяйте места, поверните обзор мышью и на телефоне. Участники остаются
   сидеть; движение, бой и интерфейс RPG отсутствуют.
4. Отправьте сообщения в чат. Перезагрузите страницу второго участника:
   список участников и посадка должны восстановиться без лишнего персонажа.
5. Выйдите из комнаты и аккаунта, затем войдите снова. Проверьте освобождение
   места; после выхода не должно оставаться активной записи микрофона.
6. В редакторе сохраните и опубликуйте тестовый шаблон с GLB, создайте по нему
   новую комнату и проверьте обстановку. Существующие комнаты сохраняют свои снимки.

Голос проверяйте отдельно через HTTPS: запись, получение другим участником
и отсутствие передачи в другую комнату. Автоматические проверки голоса
проверяют сообщения и очистку ресурсов, а не качество записи оборудования.

Старый режим сохранён в исходниках. Эта контрольная точка отделяет сценарий
переговорной; полное удаление прежнего режима не выполнялось.

## Проверка обновлённого кабинета

Этапы 0–6 редизайна по `DESIGN_SPEC.md` завершены. Обновлены кабинет `/rooms`,
приглашения `/join/:slug` и общее меню страницы аватара. API, правила доступа,
лимит пяти сохранённых комнат и работа Three.js сохранены.

После обновления откройте страницу с Ctrl+Shift+R и проверьте:

1. Вход и регистрацию, смену языка, переход к аватару и выход из аккаунта.
2. Создание комнаты, приглашение второго аккаунта, переименование, изменение
   вместимости, закрытие/открытие входа, завершение встречи и удаление.
3. Сворачивание бокового меню и сохранение его состояния; на телефоне —
   открытие/закрытие меню и доступность всех действий карточки.
4. Навигацию клавишами Tab и закрытие меню/диалогов через Escape. В опасных
   действиях начальный фокус стоит на отмене.
5. При отключении сети команды сервера блокируются, список остаётся видимым.
   После восстановления выполняется чтение данных; изменения автоматически
   не повторяются. Ошибки уведомлений можно закрыть вручную.

Обложки карточек — общие иллюстрации, не снимки реальной комнаты. Создание
предлагает существующий стандартный шаблон: API кабинета не принимает выбор
шаблона. Число участников обновляется при загрузке/обновлении списка, а не
непрерывно через WebSocket.

Автоматическая проверка интерфейса: `node scripts/test-rooms-design-browser.js`
(нужны зависимости проекта и Chromium для Playwright). Она запускает настоящий
клиент с тестовыми API без Docker и БД: проверяет ширины 320–1920 пикселей,
три языка, фокус, диалоги, состояния загрузки/ошибок/лимита/сети, очередь
уведомлений, длинные тексты и уменьшение анимации. Проверка аватара —
`node scripts/test-avatar-editor-browser.js`, переговорной —
`node scripts/test-meeting-startup-browser.js`, редактора —
`node scripts/test-room-editor-usability-browser.js`.

Эти проверки выполнены в Chromium. Они не заменяют проверку Safari/Firefox,
рабочей PostgreSQL, реальной регистрации и двух участников на сервере.
Клиент обслуживается как статические HTML/CSS/JS: отдельная сборка Vite для
него не используется. Docker-образ и VPS в ходе редизайна не запускались.

## Экран переговорной — этап 2

Администратор шаблонов может добавить один экран кнопкой «Добавить экран»
в разделе предметов редактора. Укажите центр полотна, поворот Y и размеры
в метрах; доступны пропорции 16:9/4:3. Проверьте фронт по тестовой сетке,
сохраните черновик и опубликуйте. Экран появится в новых комнатах этой версии.
Существующие снимки комнат и встроенный комплект `meeting-six-v1` не меняются.
Экран не служит родителем места, не копируется и не масштабируется как мебель.
Проверка границ учитывает центр и четыре угла, но не перекрытие мешами офиса.

В переговорной «Увеличить экран» открывает локальный просмотр: Tab удерживает
фокус, Escape закрывает диалог и возвращает фокус. Посадка и обзор сохраняются.
Сейчас отображается тестовая сетка. Загрузка PDF/изображений и общий показ
владельцем разделены на этапы 3–4 `ROOM_PRESENTATION_V1.md`; личная библиотека
реализована, общий показ ещё нет.

Обязательная миграция `add_room_presentation_screen.sql` добавляет nullable
JSONB и ограничения, не переписывая пользовательские объекты. Startup применяет
её автоматически; перед развёртыванием используйте обычную процедуру резервного
копирования и проверки миграций из `SERVER_DEPLOYMENT.md`.

Проверки этапа:

```bash
node scripts/test-room-screen.js
node scripts/test-room-screen-browser.js
node scripts/test-meeting-startup-browser.js --screen
ROOM_TEST_DATABASE_URL=postgresql://... node scripts/check-room-builtin-postgres.js
```

Последний сценарий требует отдельной тестовой PostgreSQL и создаёт/удаляет
только свои временные схемы. Проверены повторная миграция, публикация,
новый снимок с экраном, сохранность старых комнат, SQL-ограничения и запрет
привязки мест. Проверки выполнены на временной PostgreSQL 14 и в Chromium
с тестовыми API, включая мобильную ширину. PostgreSQL 18, Safari/Firefox
и реальный мобильный браузер ещё требуют проверки. VPS не обновлялся.

## Личная библиотека материалов — этап 3

В кабинете откройте меню карточки комнаты → «Материалы комнаты».
Загрузите PDF (до 20 МиБ и 100 страниц) или статическое PNG/JPEG/WebP
(до 8 МиБ и 16 млн пикселей). PDF с шифрованием/паролем и анимация отклоняются.
Библиотека ограничена 100 МиБ / 20 материалов по всем комнатам владельца;
ошибки загрузки и ожидающие удаления файлы занимают квоту до очистки.
Изображение нормализуется в WebP; во время подготовки резервируется также
место под результат. После удаления квота может освободиться через 30 секунд
или после завершения уже открытой передачи файла.

«Предпросмотр» показывает документ только вам, со сменой страниц PDF.
Он не управляет экраном участников. Закрытие окна/выход отменяет чтение и
очищает canvas. Настройки и причины ограничений — раздел 10 плана.

Материалы находятся в `uploads/room-media`, вне public, и выдаются только
по JWT владельца через `/api/my/rooms/:id/materials`. Административный токен
не даёт доступ к чужой библиотеке. При удалении комнаты файлы ставятся
на удаление в той же SQL-транзакции. В резервные копии включайте и БД,
и закрытый каталог материалов; публичную раздачу этого каталога не настраивайте.

Нужны Linux, поддерживаемый Node 20 (проверен 20.20.2, минимум 20.19),
обычная установка optional-зависимостей и обязательная миграция
`add_room_media.sql` (применяется startup). Один процесс приложения:
локальные очереди, передачи и учёт открытых читателей не распределены.
PDF.js 5.5.207/worker/шрифты обслуживаются локально, без CDN. Не обновляйте
только worker и не используйте `npm install --omit=optional`.

```bash
node scripts/test-room-media-processor.js
ROOM_TEST_DATABASE_URL=postgresql://... node scripts/check-room-media.js
node scripts/test-room-materials-browser.js
```

Проверены реальные parser/Sharp и остановка по RSS/тайм-ауту, реальный
HTTP/JWT/Multer с изолированной PostgreSQL 14, а также Chromium с тестовыми
HTTP-данными. Это не проверка Alpine/PostgreSQL 18, Safari/Firefox или реального
телефона. Перед развёртыванием нужен такой gate; VPS в этом этапе не обновлялся.

## Общий показ материалов — этап 4

В комнате, **в снимке которой уже есть экран**, владелец нажимает
«Управление показом», выбирает загруженный материал и запускает показ.
PDF можно листать, изображение имеет одну страницу. Кнопка библиотеки
открывает загрузки прямо из встречи. Участники видят общий слайд и могут
увеличить экран; масштаб просмотра меняется только у них.
Загрузка файла сама по себе показ не запускает.

Состояние сохраняется при выходе всех участников и перезапуске приложения.
«Закрыть вход» сохраняет показ, «Завершить встречу» останавливает его.
Удаление показываемого файла требует дополнительного подтверждения.
При потере связи содержимое очищается; после нового входа восстанавливается
актуальный снимок. «Обновить экран» повторяет локальную загрузку после ошибки.

Нужна обязательная миграция `add_room_presentation.sql`, применяемая startup.
Доступ участника к текущему файлу требует одновременно JWT и активной
WS-сессии/посадки: публичного URL документа нет. Поддерживается один процесс
приложения. Подробности протокола, ограничений и проверок — раздел 11
`ROOM_PRESENTATION_V1.md`.

```bash
node scripts/test-room-presentation-protocol.js
ROOM_TEST_DATABASE_URL=postgresql://... node scripts/check-room-presentation.js
node scripts/test-room-presentation-browser.js
node scripts/test-meeting-startup-browser.js --screen --builtin
```

SQL/HTTP/настоящий WS проверены на изолированной PostgreSQL 14 с шестью
зрителями и второй комнатой. Chromium проверяет настоящий рендер с тестовыми
API/WS-сообщениями; это отдельный сценарий. Ручная приёмка: два аккаунта
в комнате с экраном, PDF на нескольких страницах и изображение, поздний вход,
смена вкладки/переподключение, локальное увеличение, close/end и подтверждение
удаления активного файла. Другая комната не должна получать этот показ.
Перед развёртыванием остаются PostgreSQL 18/Alpine и реальные браузеры/телефоны.

Стандартный `meeting-six-v2` включает экран; существующие комнаты
не обновляются автоматически. VPS в этапе 4 не менялся.

## Стандартная переговорная с экраном — этап 5

На чистой установке выбирается `meeting-six-v2`: прежние офис, мебель и места
плюс экран 3,2 × 1,8 м. Центр `(7.5, 2.4, -3.1)`, поворот по Y `-π/2`:
экран обращён к участникам у торца стола. С шести мест проверены фронт,
попадание всего полотна в кадр при повороте к нему и отсутствие перекрытия
геометрией офиса/мебели. На дальних местах для мелкого текста используйте
«Увеличить экран». Проверка не моделирует перекрытие другими аватарами.

```bash
ROOM_TEST_DATABASE_URL=postgresql://... node scripts/check-room-builtin-postgres.js
ROOM_TEST_DATABASE_URL=postgresql://... node scripts/check-room-startup-postgres.js
node scripts/test-room-builtin-visibility-browser.js
node scripts/test-meeting-startup-browser.js --builtin-v2
```

Первый SQL-тест использует временные схемы. Второй требует отдельного тестового
кластера с правом `CREATE DATABASE`: создаёт и удаляет собственную временную БД,
запускает настоящий `init.sql` и все startup-миграции дважды, создаёт комнаты
двух аккаунтов и проверяет сохранность первого снимка. Файлы моделей идут
в собственный временный каталог. Проверены PostgreSQL 14 / Node 20.20.2.
Браузерные проверки используют настоящие GLB/Three.js и тестовые API.
Материалы/показ проверяются сценариями этапов 3–4; видео/PPTX сюда не входят.

Ручная приёмка перед развёртыванием: два реальных браузера/аккаунта, PDF и
изображение, переключение/увеличение, поздний вход, переподключение, close/end,
активное удаление и изоляция второй комнаты. PostgreSQL 18/Alpine, реальные
телефоны и Safari/Firefox ещё не проверены. Docker и VPS на этом этапе
не запускались, работающие шаблоны и пользовательские комнаты не менялись.

## Участники и проверка звука

В панели встречи «Участники» показывает серверный список с меткой «Вы».
При потере своего соединения список помечается неактуальным; после входа
заменяется новым снимком. Статусы различают запись сообщения и воспроизведение:
текущий голос отправляется после отпускания кнопки, а не непрерывным потоком.

В «Звук» можно выбрать микрофон, проверить уровень локально и выключить
входящее воспроизведение. Тест не отправляет запись участникам, завершается
через 30 секунд и прекращается при закрытии окна/выходе. Явно выбранный
неподключённый микрофон не заменяется другим автоматически.

План всех следующих улучшений и технологическое решение:
[MEETING_ROOM_EVOLUTION.md](MEETING_ROOM_EVOLUTION.md).
QA, ограничения и ручная приёмка первого этапа:
[meeting-controls-v1.md](docs/design-system/meeting-controls-v1.md).
Для этой порции новые SQL-миграции и npm зависимости не нужны.
